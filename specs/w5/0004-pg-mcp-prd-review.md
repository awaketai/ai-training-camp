## 1. 评审概述

本次评审针对 PostgreSQL MCP Server 产品需求文档（PRD）进行全面审查，重点关注以下方面：

- 完整性与清晰度
- 技术可行性
- 安全性考量
- API 设计
- 开放问题建议

## 2. 问题汇总

### 2.1 High 级别问题（需优先解决）

#### H1: API 设计 - 单一接口推断意图风险

| 属性 | 内容 |
|-----|------|
| **严重级别** | High |
| **类别** | Design |
| **涉及行号** | 315-321, 359-399 |

**问题描述**：

MCP 工具输入仅接受 `query` 参数，但需求文档中期望支持数据库选择、执行模式（`sql_only`、`execute`、`explain`）以及 schema 刷新/表描述等功能（F5/F7）。当前设计强制服务器推断用户意图，可能导致：
- 选择错误的数据库
- 意外执行查询（用户可能只想要 SQL）
- 无法明确控制返回行数限制

**建议**：

1. 扩展工具输入参数，包含：
   - `database`: 目标数据库名称
   - `mode`: 执行模式（`sql_only`/`execute`/`explain`）
   - `limit`: 可选的返回行数限制
2. 或者在设计说明中明确解释为何延迟这些功能，并说明服务器如何通过自然语言理解来推断意图

---

#### H2: 安全性 - 只读强制执行存在漏洞

| 属性 | 内容 |
|-----|------|
| **严重级别** | High |
| **类别** | Security |
| **涉及行号** | 124-130, 274-284, 307 |

**问题描述**：

只读强制仅依赖 `SET default_transaction_read_only = on`，但未强制要求：
- 数据库级别的最小权限角色
- 阻止锁定/副作用语句

以下语句在 read_only 模式下仍可能造成系统影响：
- `SELECT ... FOR UPDATE` / `FOR SHARE`（行级锁）
- `LISTEN` / `NOTIFY`（消息通道）
- 临时表创建
- `LOCK TABLE`

**建议**：

1. **强制要求专用只读数据库角色**，角色本身无写权限
2. **在连接字符串/角色级别强制只读**，而非仅依赖会话设置
3. **SQL 安全校验增加黑名单**：
   ```
   - SELECT ... FOR UPDATE
   - SELECT ... FOR SHARE
   - LOCK TABLE
   - LISTEN / NOTIFY
   - CREATE TEMP TABLE
   ```
4. 禁止事务级别的只读覆盖（`SET TRANSACTION READ WRITE`）

---

#### H3: 安全性 - 参数化查询未明确定义

| 属性 | 内容 |
|-----|------|
| **严重级别** | High |
| **类别** | Security |
| **涉及行号** | 255-262, 274-284, 414-423 |

**问题描述**：

需求文档在 Prompt 设计要点中提到"使用参数化查询防止注入"，但：
- 未定义模型应如何输出绑定参数 vs 字面量
- 执行器需求未明确指定使用预处理语句或绑定用户提供的值
- 如果模型将用户输入内联到 SQL 中，仍存在注入风险

**建议**：

1. **定义严格的 SQL 输出格式**：
   ```json
   {
     "sql": "SELECT * FROM users WHERE name = $1 AND status = $2",
     "params": ["张三", "active"]
   }
   ```
2. **服务端强制参数绑定**：使用 asyncpg/psycopg 的 `execute(sql, params)` 方法
3. **拒绝包含内插用户字符串的 SQL**：通过 AST 分析检测可疑的字符串拼接

### 2.2 Medium 级别问题（建议解决）

#### M1: 安全性 - Schema 发现缺少访问控制

| 属性 | 内容 |
|-----|------|
| **严重级别** | Medium |
| **类别** | Security |
| **涉及行号** | 165-175 |

**问题描述**：

Schema 发现暴露"所有用户可访问的 schema"，但未提供：
- 租户级别的 schema/表白名单
- 按请求者身份过滤元数据

在共享服务器场景下，可能导致元数据泄露给非预期的请求者。

**建议**：

1. 添加配置项限制可见的数据库/schema/表
2. 支持按部署或请求者身份过滤 MCP 响应
3. 示例配置：
   ```yaml
   access_control:
     allowed_schemas: ["public", "sales"]
     allowed_tables:
       public: ["users", "orders", "products"]
       sales: ["*"]  # 允许所有表
   ```

---

#### M2: 可行性 - 全表扫描检测缺乏可行方法

| 属性 | 内容 |
|-----|------|
| **严重级别** | Medium |
| **类别** | Feasibility |
| **涉及行号** | 282-284, 312 |

**问题描述**：

需求 F4.10 要求"检测潜在的全表扫描并警告"，但：
- 仅使用 AST/静态规则无法可靠检测
- 需要 EXPLAIN 或行数统计（`pg_class`/`pg_stats`）才能准确判断

**建议**：

1. **方案 A**：明确要求使用 `EXPLAIN` 分析查询计划
2. **方案 B**：降级为启发式警告，明确说明局限性：
   - 无 WHERE 子句的查询
   - 无索引列过滤的查询
3. 在文档中说明检测的准确性预期

---

#### M3: 完整性 - 大 Schema 处理策略缺失

| 属性 | 内容 |
|-----|------|
| **严重级别** | Medium |
| **类别** | Completeness |
| **涉及行号** | 165-231, 516-523 |

**问题描述**：

开放问题 Q3 提到超大 schema（1000+ 张表）的处理，但未在功能需求中定义：
- Schema 分块/摘要策略
- 模型上下文大小限制
- 超出限制时的降级方案

**建议**：

1. 添加 schema 处理需求：
   - **相关性过滤**：基于表/列名相似度、外键关系、使用统计
   - **上下文大小限制**：如最多传递 50 张相关表
   - **分页机制**：支持按需获取更多 schema 信息
2. 定义超出限制时的行为（报错 vs 截断 vs 智能选择）

---

#### M4: 安全性 - 审计日志缺少敏感信息脱敏

| 属性 | 内容 |
|-----|------|
| **严重级别** | Medium |
| **类别** | Security |
| **涉及行号** | 414-423 |

**问题描述**：

审计/日志需求未提及：
- 敏感查询参数脱敏
- 查询结果脱敏
- 用户标识符保护

可能导致 PII 或 API Key 泄露到日志中。

**建议**：

1. 要求结构化日志，支持可配置的字段脱敏
2. 默认排除参数值，仅记录参数指纹（hash）
3. 分离审计日志和应用日志
4. 示例日志格式：
   ```json
   {
     "timestamp": "2026-01-12T10:30:00Z",
     "request_id": "uuid",
     "user_id_hash": "sha256:xxx",
     "query_fingerprint": "SELECT * FROM users WHERE id = ?",
     "execution_time_ms": 150,
     "row_count": 10
   }
   ```

### 2.3 Info 级别问题（建议关注）

#### I1: 可行性 - NL2SQL 模型准确性

| 属性 | 内容 |
|-----|------|
| **严重级别** | Info |
| **类别** | Feasibility |
| **涉及行号** | 242-249 |

**问题描述**：

NL2SQL 准确性依赖 `gpt-4o-mini`，但：
- 复杂 JOIN/聚合可能表现不佳
- 未定义评估计划或成功阈值
- 无回退模型策略

**建议**：

1. 定义评估数据集和成功率阈值（如 >90% 简单查询，>70% 复杂查询）
2. 考虑分层模型策略：
   - `gpt-4o-mini`：草稿生成
   - 更强模型：重试/回退
3. 允许按部署配置模型选择

---

#### I2: 清晰度 - 函数白名单/黑名单未定义

| 属性 | 内容 |
|-----|------|
| **严重级别** | Info |
| **类别** | Clarity |
| **涉及行号** | 274-283 |

**问题描述**：

F4.3 提到"禁止执行存储过程/函数调用（除白名单内的聚合函数）"，但：
- 未明确哪些内置函数/聚合/窗口函数被允许
- 影响安全性和用户预期

**建议**：

文档化明确的允许/禁止列表：

**允许列表（示例）**：
- 聚合函数：`COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `ARRAY_AGG`
- 窗口函数：`ROW_NUMBER`, `RANK`, `LAG`, `LEAD`
- 标量函数：`COALESCE`, `NULLIF`, `CASE`, `CAST`, 字符串函数, 日期函数

**禁止列表（示例）**：
- 过程调用：`CALL`, `DO`
- 系统函数：`pg_sleep`, `pg_terminate_backend`
- 扩展函数：未审核的第三方扩展
- 危险操作：`COPY`, `SET`, `EXECUTE`

## 3. 开放问题建议

| 问题 | 建议 |
|-----|------|
| **Q1: 多轮对话** | 支持可选的会话状态，按 session/user 键存储，带 TTL 和大小上限；存储紧凑的对话历史 + 选定的 schema 子集；提供显式重置控制 |
| **Q2: Schema 缓存持久化** | 持久化到磁盘，带版本号和校验和；启动时加载缓存后异步验证（对比 `pg_catalog` 修改时间戳）；不匹配则全量重载 |
| **Q3: 超大 Schema** | 实现相关性过滤（表/列名相似度、外键遍历、使用统计）；限制每次 prompt 的表/列数量；允许按需调用 "describe_table" 而非全量传递 |
| **Q4: 自定义描述** | 允许可选的覆盖配置（per 表/列），带来源标签；确保覆盖按部署范围隔离且可审计 |
| **Q5: 结果验证默认值** | 默认关闭以降低延迟/成本；提供按请求标志和全局配置；跳过时记录日志；考虑对高风险模式（如自由文本过滤）自动开启 |
| **Q6: 历史/收藏** | 作为独立功能处理；如果添加，需要用户级存储、访问控制，以及保存项中的参数脱敏 |
| **Q7: 导出 CSV/JSON** | 如果添加，保持只读约束；强制行数限制/分页；需要用户明确 opt-in 和 content-type 验证 |

## 4. 评审总结

### 4.1 问题统计

| 严重级别 | 数量 | 状态 |
|---------|------|------|
| High | 3 | 需优先解决 |
| Medium | 4 | 建议解决 |
| Info | 2 | 建议关注 |

### 4.2 关键建议

1. **安全优先**：在实现前解决所有 High 级别的安全问题（H2, H3）
2. **接口设计权衡**：评估单一 `query` 接口是否满足所有使用场景，或考虑通过自然语言理解提供更明确的意图识别
3. **渐进式实现**：Medium 和 Info 级别问题可在后续版本迭代中解决
