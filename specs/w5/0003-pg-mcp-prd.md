## 1. 概述

### 1.1 项目背景

在数据分析和业务智能场景中，非技术用户经常需要从数据库中查询数据，但缺乏 SQL 编写能力。同时，即使是技术人员，面对复杂的数据库 schema 也需要花费时间理解表结构和关系。

本项目旨在构建一个基于 MCP (Model Context Protocol) 的 PostgreSQL 智能查询服务，让用户通过自然语言描述查询需求，由 AI 自动生成并执行安全的 SQL 查询。

### 1.2 项目目标

1. **降低数据查询门槛**：非技术用户可通过自然语言获取数据
2. **提高查询效率**：自动理解 schema，减少人工编写 SQL 时间
3. **保障数据安全**：仅允许只读查询，防止数据被修改或删除
4. **确保结果质量**：AI 辅助验证查询结果的有效性和相关性

### 1.3 术语定义

| 术语 | 定义 |
|-----|------|
| MCP | Model Context Protocol，Anthropic 提出的 AI 工具调用协议 |
| Schema | 数据库结构，包括表、视图、索引、类型等元数据 |
| NL2SQL | Natural Language to SQL，自然语言转 SQL 技术 |
| DDL | Data Definition Language，数据定义语言（CREATE/ALTER/DROP） |
| DML | Data Manipulation Language，数据操作语言（INSERT/UPDATE/DELETE） |
| DQL | Data Query Language，数据查询语言（SELECT） |

## 2. 用户与场景

### 2.1 目标用户

| 用户角色 | 描述 | 核心诉求 |
|---------|------|---------|
| **业务分析师** | 需要频繁查询数据做报表，但 SQL 能力有限 | 快速获取数据，无需学习复杂 SQL |
| **产品经理** | 偶尔需要查看业务数据验证产品假设 | 简单描述即可获取数据 |
| **开发工程师** | 熟悉 SQL 但不熟悉特定数据库的 schema | 快速了解表结构，生成复杂查询 |
| **数据工程师** | 需要为其他人提供数据查询能力 | 安全可控的数据访问方式 |

### 2.2 使用场景

#### 场景 1：业务数据查询

```
用户输入：查询上个月销售额最高的前10个产品，包含产品名称、销售数量和销售金额

期望输出：
- 返回 SQL：SELECT ... FROM products JOIN orders ...
- 或返回结果：表格形式的查询结果
```

#### 场景 2：数据探索

```
用户输入：用户表里有哪些字段？用户状态有哪几种？

期望输出：
- 返回用户表的 schema 信息
- 返回 user_status 字段的枚举值
```

#### 场景 3：复杂统计分析

```
用户输入：统计每个部门的员工数量、平均工资，按员工数量降序排列

期望输出：
- 生成包含 GROUP BY、AVG、ORDER BY 的 SQL
- 执行并返回统计结果
```

#### 场景 4：仅获取 SQL

```
用户输入：帮我写一个查询，找出过去7天内注册但未下单的用户，只要SQL不要执行

期望输出：
- 仅返回生成的 SQL 语句，不执行
```

### 3.2 F1: 数据库连接管理

#### 3.2.1 功能描述

MCP Server 启动时读取配置，建立与一个或多个 PostgreSQL 数据库的连接。

#### 3.2.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F1.1 | 支持通过配置文件定义多个数据库连接 | P0 |
| F1.2 | 支持的连接参数：host, port, database, user, password | P0 |
| F1.3 | 支持通过环境变量配置敏感信息（密码） | P0 |
| F1.4 | 支持连接池管理，复用数据库连接 | P1 |
| F1.5 | 支持连接健康检查和自动重连 | P1 |
| F1.6 | 支持 SSL/TLS 加密连接 | P1 |
| F1.7 | 支持只读连接模式（SET default_transaction_read_only = on） | P0 |

#### 3.2.3 配置示例

```yaml
# config.yaml
databases:
  - name: "sales_db"
    host: "localhost"
    port: 5432
    database: "sales"
    user: "readonly_user"
    password: "${SALES_DB_PASSWORD}"  # 环境变量引用
    ssl_mode: "require"
    read_only: true

  - name: "analytics_db"
    host: "analytics.example.com"
    port: 5432
    database: "analytics"
    user: "analyst"
    password: "${ANALYTICS_DB_PASSWORD}"
    read_only: true
```

### 3.3 F2: Schema 发现与缓存

#### 3.3.1 功能描述

启动时自动发现并缓存所有可访问数据库的 schema 信息，为 NL2SQL 提供上下文。

#### 3.3.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F2.1 | 发现所有用户可访问的 schema（排除系统 schema） | P0 |
| F2.2 | 获取每个 schema 下的所有表（tables） | P0 |
| F2.3 | 获取每个 schema 下的所有视图（views） | P0 |
| F2.4 | 获取每个表/视图的列信息（列名、数据类型、是否可空、默认值、注释） | P0 |
| F2.5 | 获取主键、外键约束信息 | P0 |
| F2.6 | 获取索引信息 | P1 |
| F2.7 | 获取自定义类型（ENUM、复合类型） | P1 |
| F2.8 | 获取表和列的注释（COMMENT） | P0 |
| F2.9 | 支持手动刷新 schema 缓存 | P1 |
| F2.10 | 支持定时自动刷新 schema 缓存 | P2 |
| F2.11 | Schema 信息持久化到本地文件，加速重启 | P2 |

#### 3.3.3 缓存的 Schema 结构

```python
# 期望的 Schema 数据结构示例
{
    "database_name": "sales_db",
    "schemas": [
        {
            "name": "public",
            "tables": [
                {
                    "name": "orders",
                    "comment": "订单表",
                    "columns": [
                        {
                            "name": "id",
                            "type": "bigint",
                            "nullable": False,
                            "primary_key": True,
                            "comment": "订单ID"
                        },
                        {
                            "name": "user_id",
                            "type": "bigint",
                            "nullable": False,
                            "foreign_key": {
                                "table": "users",
                                "column": "id"
                            },
                            "comment": "用户ID"
                        },
                        # ...
                    ],
                    "indexes": [
                        {
                            "name": "idx_orders_user_id",
                            "columns": ["user_id"],
                            "unique": False
                        }
                    ]
                }
            ],
            "views": [...],
            "types": [
                {
                    "name": "order_status",
                    "type": "enum",
                    "values": ["pending", "paid", "shipped", "completed", "cancelled"]
                }
            ]
        }
    ]
}
```

### 3.4 F3: 自然语言转 SQL (NL2SQL)

#### 3.4.1 功能描述

接收用户的自然语言查询需求，结合数据库 schema 信息，调用 OpenAI GPT 模型生成 SQL。

#### 3.4.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F3.1 | 调用 OpenAI API（模型：gpt-4o-mini）生成 SQL | P0 |
| F3.2 | 将相关的 schema 信息作为上下文传递给模型 | P0 |
| F3.3 | 支持指定目标数据库（当配置多个数据库时） | P0 |
| F3.4 | 智能选择相关的表，避免传递过多无关 schema | P1 |
| F3.5 | 支持多轮对话，理解上下文中的指代 | P2 |
| F3.6 | 生成的 SQL 应包含适当的注释说明 | P1 |
| F3.7 | 支持配置 OpenAI API Key 和 Base URL（兼容其他 OpenAI 兼容接口） | P0 |
| F3.8 | 支持配置模型参数（temperature、max_tokens 等） | P1 |

#### 3.4.3 Prompt 设计要点

生成 SQL 的 Prompt 应包含：

1. **角色设定**：PostgreSQL 专家，只生成安全的只读查询
2. **Schema 上下文**：相关表的结构、关系、注释
3. **约束条件**：
   - 只生成 SELECT 语句
   - 使用参数化查询防止注入
   - 对大表添加 LIMIT 限制
   - 优先使用索引列进行过滤
4. **输出格式**：纯 SQL，可执行，带注释

### 3.5 F4: SQL 安全校验

#### 3.5.1 功能描述

对生成的 SQL 进行安全检查，确保只允许执行只读查询，防止数据被修改或系统被攻击。

#### 3.5.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F4.1 | **白名单机制**：仅允许 SELECT 语句 | P0 |
| F4.2 | **黑名单拦截**：禁止 INSERT/UPDATE/DELETE/DROP/TRUNCATE/ALTER/CREATE | P0 |
| F4.3 | 禁止执行存储过程/函数调用（除白名单内的聚合函数） | P0 |
| F4.4 | 禁止 COPY 命令 | P0 |
| F4.5 | 禁止访问系统表（pg_catalog 等，除非明确允许） | P1 |
| F4.6 | 检测并拦截 SQL 注入尝试 | P0 |
| F4.7 | 限制子查询嵌套深度（默认最大 3 层） | P1 |
| F4.8 | 限制 JOIN 表数量（默认最大 5 个） | P2 |
| F4.9 | 强制添加 LIMIT（若用户未指定，默认 1000） | P0 |
| F4.10 | 检测潜在的全表扫描并警告 | P2 |

#### 3.5.3 安全校验流程

```
用户输入 → NL2SQL生成 → SQL解析(AST) → 安全规则校验 → 通过/拒绝
                                              │
                                              ├── 语句类型检查
                                              ├── 关键字黑名单
                                              ├── 函数白名单
                                              ├── 表访问权限
                                              └── 复杂度限制
```

### 3.6 F5: SQL 执行与测试

#### 3.6.1 功能描述

执行通过安全校验的 SQL，获取查询结果，并进行基本的可执行性测试。

#### 3.6.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F5.1 | 在只读事务中执行 SQL | P0 |
| F5.2 | 设置查询超时时间（默认 30 秒，可配置） | P0 |
| F5.3 | 限制返回结果行数（默认 1000 行，可配置） | P0 |
| F5.4 | 捕获并友好展示 SQL 执行错误 | P0 |
| F5.5 | 记录 SQL 执行耗时 | P1 |
| F5.6 | 支持 EXPLAIN 分析查询计划（可选） | P2 |
| F5.7 | 大结果集分页返回 | P2 |

#### 3.6.3 执行模式

| 模式 | 描述 | 返回内容 |
|-----|------|---------|
| `sql_only` | 仅生成 SQL，不执行 | SQL 语句 |
| `execute` | 生成并执行 SQL | 查询结果（默认） |
| `explain` | 生成 SQL 并返回执行计划 | SQL + EXPLAIN 结果 |

### 3.7 F6: 结果验证与解释

#### 3.7.1 功能描述

调用 AI 对查询结果进行验证和解释，确保结果与用户意图匹配，并提供人类可读的解释。

#### 3.7.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F6.1 | 将用户输入、生成的 SQL、部分结果发送给 AI 验证 | P1 |
| F6.2 | AI 判断结果是否符合用户意图 | P1 |
| F6.3 | 若结果可能不符合预期，返回警告信息 | P1 |
| F6.4 | 生成结果的自然语言摘要/解释 | P2 |
| F6.5 | 结果验证为可选功能，可通过配置开关 | P1 |
| F6.6 | 限制发送给 AI 的结果数据量（如仅前 10 行） | P0 |

#### 3.7.3 验证场景示例

```
用户输入：查询上月销售额最高的产品
生成 SQL：SELECT * FROM products ORDER BY price DESC LIMIT 10
执行结果：返回了按价格排序的产品（而非按销售额）

AI 验证发现：
- 用户要求"销售额最高"
- SQL 按 price（单价）排序，而非 sales_amount（销售额）
- 返回警告："查询结果按产品单价排序，可能不是您期望的销售额排序。是否需要重新生成？"
```

### 3.8 F7: MCP 协议接口

#### 3.8.1 功能描述

实现 MCP 协议，提供标准化的工具接口供 AI 客户端调用。

#### 3.8.2 功能要求

| 编号 | 要求 | 优先级 |
|-----|------|-------|
| F7.1 | 实现 MCP Server 标准协议 | P0 |
| F7.2 | 提供 `query` 工具：自然语言查询 | P0 |
| F7.3 | 支持 stdio 传输方式 | P0 |
| F7.4 | 支持 SSE (Server-Sent Events) 传输方式 | P2 |

#### 3.8.3 MCP 工具定义

```json
{
  "tools": [
    {
      "name": "pg_query",
      "description": "使用自然语言查询 PostgreSQL 数据库。支持自然语言描述的数据查询需求，自动生成并执行安全的 SQL 查询。",
      "inputSchema": {
        "type": "object",
        "properties": {
          "query": {
            "type": "string",
            "description": "自然语言描述的查询需求，例如：'查询上个月销售额最高的前10个产品' 或 '用户表里有哪些字段'"
          }
        },
        "required": ["query"]
      }
    }
  ]
}
```

> **设计说明**：当前版本仅提供 `pg_query` 单一接口，通过自然语言理解自动处理以下场景：
> - **数据查询**：自动生成 SQL 并执行，返回查询结果
> - **Schema 探索**：识别用户询问表结构的意图，返回相关 schema 信息
> - **仅返回 SQL**：当用户明确表示"只要 SQL"时，仅返回生成的 SQL 不执行
>
> 后续版本可根据需要扩展 `pg_list_databases`、`pg_describe_table`、`pg_refresh_schema` 等辅助工具。

## 4. 非功能需求

### 4.1 性能要求

| 指标 | 要求 |
|-----|------|
| Schema 加载时间 | 单个数据库 < 10 秒（100 张表规模） |
| NL2SQL 生成时间 | < 5 秒（不含网络延迟） |
| SQL 执行超时 | 可配置，默认 30 秒 |
| 并发请求 | 支持至少 10 个并发查询 |

### 4.2 安全要求

| 要求 | 说明 |
|-----|------|
| 数据库凭证保护 | 密码不得明文存储，支持环境变量注入 |
| 只读强制 | 数据库连接强制只读模式 |
| SQL 注入防护 | 使用参数化查询，AST 级别的安全检查 |
| API Key 保护 | OpenAI API Key 不得暴露在日志中 |
| 审计日志 | 记录所有查询请求和执行的 SQL |

### 4.3 可靠性要求

| 要求 | 说明 |
|-----|------|
| 错误处理 | 所有异常应被捕获并返回友好错误信息 |
| 连接恢复 | 数据库连接断开后自动重连 |
| 降级策略 | OpenAI 服务不可用时返回明确错误 |

### 4.4 可观测性要求

| 要求 | 说明 |
|-----|------|
| 日志 | 结构化日志，支持 JSON 格式输出 |
| 指标 | 暴露查询次数、成功率、延迟等指标 |
| 追踪 | 支持请求链路追踪（可选） |

## 6. 验收标准

### 6.1 功能验收

| 场景 | 验收标准 |
|-----|---------|
| 基本查询 | 用户输入"查询所有用户"，返回正确的 SQL 和结果 |
| 复杂查询 | 用户输入包含 JOIN、GROUP BY、ORDER BY 的需求，生成正确 SQL |
| 安全拦截 | 用户尝试"删除所有用户"，系统拒绝执行并返回错误 |
| 多数据库 | 配置多个数据库，用户可指定查询目标 |
| 仅 SQL 模式 | 用户指定只要 SQL，系统不执行直接返回 |
| 结果验证 | AI 发现 SQL 可能不符合意图时给出警告 |

### 6.2 性能验收

| 场景 | 验收标准 |
|-----|---------|
| 启动速度 | 100 张表的数据库，schema 加载 < 10 秒 |
| 响应速度 | 简单查询端到端响应 < 8 秒 |

### 6.3 安全验收

| 场景 | 验收标准 |
|-----|---------|
| DDL 拦截 | 任何 CREATE/ALTER/DROP 语句被拦截 |
| DML 拦截 | 任何 INSERT/UPDATE/DELETE 语句被拦截 |
| 注入防护 | SQL 注入尝试被识别并拦截 |
| 只读连接 | 即使绕过检查，数据库层面也拒绝写入 |

## 8. 开放问题

以下问题需要在设计阶段进一步讨论：

| 编号 | 问题 | 影响范围 |
|-----|------|---------|
| Q1 | 是否需要支持多轮对话（记住上下文）？如果是，上下文如何存储和管理？ | F3 |
| Q2 | Schema 缓存是否需要持久化？重启后是重新加载还是读取缓存？ | F2 |
| Q3 | 对于超大 schema（1000+ 张表），如何优化传递给 AI 的上下文？ | F3 |
| Q4 | 是否需要支持用户自定义的表/列描述，覆盖数据库中的 COMMENT？ | F2 |
| Q5 | 结果验证功能是否默认开启？开启后会增加延迟和成本 | F6 |
| Q6 | 是否需要支持查询历史记录和收藏功能？ | 新功能 |
| Q7 | 是否需要支持查询结果导出（CSV/JSON）？ | 新功能 |
